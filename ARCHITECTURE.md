# Architecture

## Current phase

Phase 5 adds an independent SQS FIFO consumer with transactional Inbox coordination, retry, and DLQ handling. Phase 4 recovery for out-of-order wager references and multiprocess validation remain in place. PostgreSQL-backed wager processing, persistent idempotency, wallet-scoped locking, REST submission and lookup, and transactional outbox writes remain the financial core. The financial domain lives under `src/domain` and imports no NestJS, ORM, PostgreSQL, or SQS packages.

## Initial decisions

- Bun 1.4.3 is the runtime, package manager, and test runner; TypeScript strict mode is enabled.
- `scripts/bootstrap.sh` installs the pinned Bun release when it is missing, then runs `bun install --frozen-lockfile`, typecheck, and build. `DEVELOPMENT.md` describes the reproducible local setup.
- Unit tests use Bun's test runner and are typechecked through `tsconfig.test.json`.
- NestJS 11 hosts the HTTP application.
- MikroORM 7.2.0 with its PostgreSQL driver and migration extension maps persistence-only records under `src/persistence/entities.ts`. Domain values are rehydrated through each domain class's `rehydrate` factory.
- The `WalletOpeningService` application use case depends on `WalletPersistencePort`; `WalletPostgresAdapter` owns MikroORM, SQL, and PostgreSQL error translation. The HTTP controller does not contain persistence rules.
- PostgreSQL 17 and LocalStack SQS 4.12.0 are isolated local dependencies in Docker Compose. This is the last pre-authentication LocalStack image selected for this local test stack; no user token is required.
- LocalStack has separate FIFO command, dead-letter, and event queues. Broker deduplication is not a correctness guarantee.
- No identity provider is configured in Phase 0. The challenge permits documenting an identity-provider extension point; no custom password authentication will be added.
- The application exposes `/health/live` without dependency checks. Readiness will be added with the persistence and messaging adapters.

## Financial consistency

The domain enforces exact `bigint` minor-unit arithmetic, matching currencies, non-negative wallet and ledger balances, balanced immutable ledger entries, explicit wager states, and the business direction of BET, WIN, LOSS, REFUND, and ROLLBACK. Wallet movements return the ledger entry that records the same before and after balance.

## PostgreSQL persistence and Phase 2 scope

`src/persistence/migrations/Migration20261022090000.ts` creates wallets, wager transactions, ledger entries, inbox records, and outbox records. `Migration20261022100000` adds the stable ledger cursor index and blocks `TRUNCATE` in addition to row updates and deletes. `Migration20261022110000` adds child-side FK indexes for wallet, reference, and transaction lookups. Monetary columns use `NUMERIC(38,2)` and are read as decimal strings; neither the domain nor persistence adapters convert an amount to JavaScript `number`.

Wallet opening runs in one `EntityManager.transactional()` scope. A zero opening inserts only the wallet. A positive opening inserts the wallet, an internal processed `OPENING` wager with a stored result balance, and one `CREDIT` ledger row. The unique `(player_id,currency)` constraint arbitrates concurrent creation; the losing transaction rolls back and the API returns 409.

The schema enforces non-negative wallet and ledger balances, version >= 1, provider idempotency and external-operation uniqueness, one ledger row per wallet/transaction, exact before/after arithmetic, transaction/wallet/currency foreign keys, and one processed reversal of a given kind per reference. An append-only trigger rejects ledger UPDATE, DELETE, and TRUNCATE. Partial indexes cover pending-reference work, due outbox work, processed reversal uniqueness, and non-null reference lookups; a `(wallet_id,created_at,id)` index serves stable ledger pages. Child-side wallet and transaction indexes support FK checks and wallet lookup. Unique constraints provide the lookup indexes for wallets, provider idempotency, external transaction, and wallet/transaction keys.

The `GET /wallets/:walletId/ledger` cursor is opaque base64url over `(createdAt,id)` and pages in stable descending order. Reconciliation reads the materialized balance and ledger aggregate in a repeatable-read transaction; it reports a difference and never repairs data.

`bun run db:migrate` applies migrations. `bun run db:rollback` reverses the latest migration. Migrations are not automatically run by API startup. PostgreSQL-backed tests use an explicitly named disposable database (`wagering_phase2_test`) and verify `up → down → up` before exercising SQL guarantees. `docker-compose.yml` gives the API a container-network database URL; local Bun commands use the `DATABASE_URL` in `.env.example`.

The wallet-opening use case depends on `WalletPersistencePort`; `WalletPostgresAdapter` implements that port. The shared `ProcessWagerService` owns the MikroORM transaction boundary and is invoked by both the HTTP route and the standalone SQS consumer. Domain rules remain in the existing aggregates; there is no second financial implementation in the SQS handler.

## Phase 3 wagering consistency

`POST /wagering/transactions` requires `Idempotency-Key`. The service hashes canonical JSON with recursively sorted object keys over normalized business request fields; transport headers are excluded. PostgreSQL constraints on `(provider_id,idempotency_key)` and `(provider_id,external_transaction_id)` remain the final deduplication authority. Identical replays read the stored response snapshot, including its original status, failure code, and balance; key reuse with a different hash returns 409. A pending-reference replay retains its original pending status and accepted balance snapshot even after the worker resolves it. Transaction lookup reports the current persisted state and its outcome balance snapshot, never a live wallet balance.

Each operation runs in one PostgreSQL transaction. The wallet row is locked using `SELECT ... FOR UPDATE` before reading or changing its balance. Distinct wallets do not share a lock. Deadlock and serialization errors are retried twice after the initial attempt; exhausted transient retries map to HTTP 503. Wallet is the first lock; a referenced wager on that wallet is locked next. No external call occurs inside the transaction.

Processed, rejected, and pending-reference outcomes persist with stable failure codes and response balance snapshots. BET debits; WIN and REFUND credit; LOSS records no ledger or balance event; ROLLBACK reverses the referenced financial direction. Reversals require an existing processed reference, exact amount equality, matching provider/player/wallet/round/currency, and the database partial unique reversal index. Missing or not-yet-processed REFUND/ROLLBACK references persist as `PENDING_REFERENCE`, without ledger movement. The standalone pending-reference worker claims due rows with a short SQL transaction using `FOR UPDATE SKIP LOCKED`, stores a per-row lease, then resumes work after acquiring wallet, pending wager, and reference locks in that order. A process crash leaves the lease to expire; another worker may reclaim the row. Retries use deterministic exponential backoff (60 seconds initial, capped at 30 minutes), a 24-hour reference TTL, and a maximum of 64 attempts. The worker reuses domain validation and writes final wager state, ledger, result snapshot, and outbox events in one database transaction. It emits no duplicate pending event while rescheduling. Invalid, terminal, expired, or exhausted references are rejected with a stable failure code.

Financial result, wallet update, optional immutable ledger row, and corresponding outbox envelopes share the same commit. `WalletBalanceChanged` is stored only when balance changed. Positive wallet opening also writes `WagerTransactionProcessed` and `WalletBalanceChanged` in its existing atomic transaction.

The standalone `sqs-consumer` process uses AWS SDK for JavaScript v3 and long-polls `wager-transactions.fifo`. It identifies Inbox rows by a stable `consumerName` and SQS `messageId`, and records a SHA-256 hash of canonical JSON for the complete validated envelope. Inbox insertion/completion, wager outcome, wallet update, optional ledger row, and outbox events share the existing `ProcessWagerService` SQL transaction. Matching processed Inbox redelivery is acknowledged without financial work; a reused message ID with a different hash is treated as a permanent conflict. Business rejections and durable `PENDING_REFERENCE` outcomes are acknowledged after commit; the latter continues through the existing pending-reference worker. Transient failures release the current receipt handle with bounded exponential visibility delay; permanently invalid messages are left for the configured SQS redrive policy (`maxReceiveCount=5`) to move them to `wager-transactions-dlq.fifo`. No financial consistency depends on SQS deduplication or process memory.

The command queue visibility timeout is 60 seconds. The consumer requests up to ten messages with a 20-second long poll and renews visibility while processing. It processes messages in a FIFO group sequentially while allowing distinct groups to run concurrently. Producers should set `MessageGroupId` to the wallet ID when valid; the consumer still relies on PostgreSQL wallet row locks for correctness. A poison message blocks later messages in its FIFO group until resolved or moved to the DLQ, so inspect the DLQ body, attributes, and receive count before redriving. SIGTERM stops new polling and drains the active batch before the Compose 90-second grace period expires. A crash after SQL commit but before SQS deletion is safe: redelivery observes the committed Inbox and performs no second financial effect.

Lock review: wager processing takes the wallet row before a referenced wager row. The pending-reference worker uses wallet → pending wager → referenced wager; it holds the pending row lock after checking its lease, so a competing claimant cannot take ownership during the financial transaction. SQS Inbox locking happens before wager processing, but HTTP processing never locks Inbox rows, and separate Inbox rows do not create a cycle with wallet/reference locks. Pending idempotency snapshots intentionally remain the original `PENDING_REFERENCE` acceptance result after background resolution, while lookup exposes the current transaction status and persisted outcome balance.

`Migration20261022120000` adds reference expiry and worker lease columns, backfills existing pending rows with a 24-hour expiration and retry schedule, and rebuilds the pending-work index. The API, pending-reference worker, and SQS consumer are independent processes and use the same PostgreSQL database. The outbox publisher remains Phase 6.
